# Алгоритм генерации таблицы Раздела II

Документ описывает **полный пайплайн «под капотом»**, который запускается из UI «Инструменты → АЗ», когда пользователь загружает аудиторское заключение (АЗ) и получает `.docx` со сводной таблицей Раздела II.

Код парсинга и сборки живёт на backend (`sokol-backend/app/services/reports/section_ii/`). Frontend только выбирает файл, вызывает API и скачивает результат.

---

## 1. Точка входа с UI

| Действие в UI | API | Флаг |
|---------------|-----|------|
| «Генерация Раздела II» | `POST /api/v1/tools/section-ii` | `with_hyperlinks=False` |
| «Генерация Раздела II (с гиперссылками)» | `POST /api/v1/tools/section-ii-links` | `with_hyperlinks=True` |

**Frontend:** `ToolsTab` → `generateSectionIITemplate` / `generateSectionIIWithLinks` (`src/api/tools.ts`).

**Backend:** `instruments_reports.py` → сохраняет upload во временный `.docx` → `docx_generator.process_document(...)` в thread pool → отдаёт файл (`*_section_ii.docx` или `*_section_ii_links.docx`).

Ограничения upload: только `.docx`, лимит `SOKOL_MAX_UPLOAD_MB` (по умолчанию 100 МБ).

```mermaid

  participant UI as ToolsTab
  participant API as /tools/section-ii*
  participant GEN as process_document
  participant PAR as parse_observations_from_file_with_runs

  UI->>API: UploadFile (.docx)

  PAR-->>GEN: List[Observation]
  opt with_hyperlinks
    GEN->>GEN: закладки SokolObs* на абзацы наблюдений

  GEN->>TBL: heading + table XML
  GEN->>GEN: безопасная вставка после Раздела I
  GEN-->>API: output.docx
  API-->>UI: download blob
```

## 2. Общая идея

1. **Источник данных** — Раздел III (детальные результаты): блоки «Наблюдение X.Y[.Z]», тело, уровень существенности, рекомендации, срок.
2. **Результат** — Раздел II: заголовок + сводная таблица «Основные нарушения и недостатки / Существенность / Рекомендация».
3. **Метод правки документа** — не `python-docx` для записи, а **копирование OOXML ZIP** и точечная замена куска `word/document.xml`, чтобы сохранить титул, оглавление, стили, шрифты и остальные части пакета.

## 3. Оркестратор `process_document`

Файл: `section_ii/docx_generator.py`.

### Шаг A. Копия и очистка

1. `shutil.copy2(input → output)`.
2. Читается `word/document.xml`.
3. Удаляется **ранее сгенерированный** SOKOL-раздел II (распознаётся по характерному тексту сводной таблицы), чтобы повторная генерация не парсила старую таблицу как наблюдения и не дублировала раздел.

### Шаг B. Парсинг наблюдений

Вызов `_parse_observations_from_stripped_docx` → `parse_observations_from_file_with_runs`.

Если список пуст → ошибка: *«Наблюдения не найдены…»*.

### Шаг C. Картинки существенности

По уровням `низкий` / `средний` / `высокий` в пакет добавляются PNG из `data/images/` (`green.png`, `yellow.png`, `red.png`), обновляются `document.xml.rels` и `[Content_Types].xml`.

### Шаг D. Гиперссылки (опционально)

Если `with_hyperlinks=True`:

1. До вставки таблицы в XML абзацев наблюдений ставятся закладки `SokolObs…` (`observation_links.ensure_observation_bookmarks`).
2. В таблице название наблюдения станет hyperlink на эту закладку.
3. Если закладки не нашлись для всех номеров — генерация прерывается с ошибкой.

### Шаг E. Точка вставки Раздела II

Защита структуры АЗ:

1. Страницы 1–2 (титул + содержание) **не трогаются** — граница `find_first_block_after_page2`.
2. Обязателен Раздел I («Аудиторское мнение»).
3. Если Раздел II уже есть после I — он **заменяется** целиком.
4. Если Раздела II нет — вставка **после Раздела I**, перед Разделом III.
5. Проверки: insert не в титуле/оглавлении, не до Раздела I; после замены XML-префикс до точки вставки байт-в-байт совпадает с исходным.

### Шаг F. Сборка XML

1. Преобладающий шрифт документа (`fonts.get_predominant_font`).
2. Текст/стиль заголовка II (из старого заголовка или дефолт: *«II. Основные результаты аудита и аудиторские рекомендации»*).
3. Закладки оглавления на заголовок II (`bookmark_utils`).
4. `table_builder.create_heading_paragraph_xml` + `create_table_xml(observations, …)`.
5. Замена диапазона блоков в `document.xml`, запись ZIP.

## 4. Парсинг наблюдений (ядро)

Главная функция: `docx_parser.parse_observations_from_file_with_runs`.

### 4.1. Разбор документа в блоки

`docx_blocks.extract_document_blocks`:

- Обход `w:body`: абзацы (`p`) и таблицы (`tbl` → ячейки).
- Каждый блок: `text`, `runs` (фрагменты с форматированием), индексы таблицы/ячейки/строки.
- Флаг `has_frame_border` — абзац в «рамочке» (часто там рекомендация / существенность / срок).
- Отдельно собираются textbox’ы (`txbxContent`), привязанные к якорю-абзацу.

### 4.2. Где начинается «тело» Раздела III

`heading_detection.find_section3_flat_block_idx`:

- Игнорирует оглавление и титул (поиск «тела» после TOC / Раздела I–II).
- Кандидаты старта: настоящий заголовок раздела ≥ III **или** первое наблюдение с номером `≥ 3.x`.
- Берётся **минимальный** индекс среди кандидатов, чтобы не пропустить наблюдения раздела 3 до заголовка IV.

### 4.3. Порядок наблюдений

`_iter_observation_starts(blocks, section3_start)`:

1. Идёт по блокам **строго сверху вниз**.
2. Пропускает:
   - всё до старта Раздела III;
   - ячейки уже сгенерированной SOKOL-сводки (`find_sokol_summary_block_indices`);
   - абзацы с frame-border (это не заголовок наблюдения);
   - ячейки не первой колонки таблицы.
3. Матч заголовка: `OBS_BLOCK_START_RE` —  
   `Наблюдение` / `Наблюдения` + опционально `№|N|No.` + номер `3.1`, `3.1.1`, `4.2` …
4. Каждое номерное наблюдение берётся **один раз** (первое вхождение).

Именно этот порядок определяет строки таблицы (никакой «дописки в конец» и сортировки по номеру).

### 4.4. Текстовый парсинг полей

Из блоков начиная с Раздела III склеивается текст → `field_parser.parse_text_observations`:

| Поле | Как извлекается |
|------|-----------------|
| `number` | Группа из `OBS_LINE_START_RE` (только **начало строки**, чтобы «см. Наблюдение 4.1» внутри текста не создавало ложное наблюдение) |
| `chapter` / `chapter_title` | Ближайший предыдущий заголовок главы/раздела (`Глава`/`Раздел`/`III. …`) |
| `name` | `extract_name_from_text` (см. ниже) |
| `materiality_level` | `Уровень существенности: низкий\|средний\|высокий`, иначе `"не указан"` |
| `recommendations` + `rec_label` | Блок после «Аудиторская рекомендация / Рекомендация / Мероприятия после аудита» |
| `deadline` | Хвост `Срок … ДД.ММ.ГГГГ` (в т.ч. интервал `с … по …`) |

### 4.5. Название наблюдения (`name`) — важный нюанс

`extract_name_from_text`:

1. Обрезает блок по cutoff-паттернам (`NAME_CUTOFF_PATTERNS`):
   - тело: `Проверкой установлено`, `В ходе проверки установлено`, `В результате проверки`;
   - поля: `Уровень существенности`, `Аудиторск… рекомендац…`, `Рекомендаци[яи]:`, `Мероприятия после аудита`.
2. Берёт **первую непустую строку** — это заголовок в отдельном абзаце АЗ.
3. Если всё ещё длиннее 120 символов — мягкое усечение с `...`.

Типичная структура в АЗ:

```text
Наблюдение 3.1.1. <Название одной строкой>
Проверкой установлено <описание нарушения…>
Уровень существенности: низкий
Аудиторские рекомендации: …
Срок – 01.10.2026.
```

Без шагов 1–2 в колонку «название» раньше попадал хвост «Проверкой установлено…».

### 4.6. Обогащение runs и рамок

После текстового парсинга для каждого наблюдения:

1. **Имя из таблицы** (если в Разделе III наблюдение оформлено 2-колоночной таблицей «номер | название»):  
   `extract_name_runs_from_tables` → `name_runs` + перезапись `name` (с сохранением форматирования).
2. **Глава** уточняется через `build_block_heading_state` (в т.ч. «свободные» римские заголовки `III. …` по стилю/жирности).
3. **Рекомендации** — приоритет источников:
   1. textbox в диапазоне наблюдения;
   2. группа абзацев с `has_frame_border` (рамочка);
   3. таблица с полями рекомендации / объекта аудита / срока;
   4. иначе обычные абзацы → `rec_runs`.
4. Из рамок/таблиц могут получиться несколько `RecommendationEntry` (несколько строк «Рекомендация» в таблице II).
5. Материальность, срок, `rec_label` дополнительно пересчитываются по тексту всех блоков наблюдения (включая рамки).

```mermaid
flowchart TD
  A[DOCX ZIP] --> B[document.xml → DocumentBlock[]]
  B --> C[find_section3_flat_block_idx]
  C --> D[_iter_observation_starts]
  D --> E[parse_text_observations]
  E --> F[extract_name_from_text + cutoff]
  B --> G[extract_name_runs_from_tables]
  G --> H{есть name в таблице?}
  H -->|да| I[name / name_runs из ячейки]
  H -->|нет| F
  F --> J[Observation]
  I --> J
  J --> K[рамки / textbox / таблицы → rec_entries]
  K --> L[materiality + deadline]
  L --> M[List Observation]
```

## 5. Модель данных строки таблицы

`Observation` (`models.py`):

| Поле | В таблице Раздела II |
|------|----------------------|
| `number` | «Наблюдение 3.1.1.» |
| `chapter` + `chapter_title` | Строка-разделитель главы (`III. …`) перед группой |
| `name` / `name_runs` | Название нарушения (курсив; hyperlink в links-режиме) |
| `materiality_level` | Цветная иконка (или текст, если картинки нет) |
| `rec_label` | Подпись ячейки («Рекомендация» / «Мероприятия после аудита») |
| `recommendations` / `rec_runs` / `rec_entries` | Текст рекомендации + срок |
| `deadline` | Дописывается к рекомендации, если не уже внутри runs |

---

## 6. Сборка таблицы

`table_builder.create_table_xml`:

1. Шапка: «Основные нарушения и недостатки» | «Существенность».
2. Для каждого наблюдения по порядку парсера:
   - при смене главы — строка заголовка главы на всю ширину;
   - строка наблюдения: номер | название | иконка существенности;
   - строка(и) рекомендации: подпись | текст (с переносами абзацев, alignment both).
3. Шрифт — преобладающий в документе.
4. В режиме hyperlinks название — ссылка `w:anchor` на закладку наблюдения в Разделе III.

## 8. Типичные причины «кривой» таблицы

| Симптом | Что проверить в АЗ / парсере |
|---------|------------------------------|
| Пустой результат | Нет строк вида `Наблюдение X.Y` в теле (не только в оглавлении) |
| Лишний текст в названии | Тело без абзацного разрыва / без маркера вроде «Проверкой установлено» |
| Пропали наблюдения раздела 3 | Старт парсинга уехал из‑за ложных «I/II/III» в таблицах титула (кварталы и т.п.) |
| Дубли / мусор из старой сводки | Не сработал strip старого Раздела II / SOKOL-таблица не распознана |
| Нет гиперссылок | Абзац наблюдения не найден для закладки (`section-ii-links`) |
| «Не найден раздел I» | В теле нет «Аудиторское мнение» / Раздела I после оглавления |
