# Индикаторы и автостатус рекомендаций

Это ядро карточки рекомендации: два значка в таблице и на форме считаются **не вручную**, а правилами. Одинаковая логика на backend и frontend. Менять правила только здесь и в двух модулях ниже, синхронно.

| Слой | Файл |
|------|------|
| Правила (Python) | `sokol-backend/app/services/recommendation_status.py` |
| Правила (TS) | `sokol-frontend/src/utils/recommendationAutoStatus.ts` |
| Карточка | `sokol-frontend/src/utils/recommendationFormAutoStatus.ts` |
| Импорт из АЗ | `sokol-frontend/src/utils/checkRecommendationsPreview.ts` |
| Persist + сутки | `recommendations_service.overlay_computed_status_fields`, `recommendation_status_refresh.py` |
| Иконки | `sokol-frontend/src/components/recommendations/indicatorIcons.ts` |

Тесты: `sokol-backend/tests/test_recommendation_status.py`, `recommendationAutoStatus.test.ts`, `recommendationFormAutoStatus.test.ts`, `checkRecommendationsPreview.test.ts`.

## Что хранится

Две независимые оси, но автоматика всегда пишет их **парой**.

| Поле | Смысл | Откуда на форме |
|------|--------|-----------------|
| `deadline` | Срок контроля | поле «Срок контроля»; при переносе **перезаписывается** датой переноса |
| `actual_completion_date` | Срок исполнения | контрольная зона, блок «Срок исполнения» |
| `deadline_extensions` | Переносы срока | контрольная зона, «Перенос срока» (дата + комментарий) |
| `control_removals` | Снятие с контроля | контрольная зона, «Снять с контроля» |
| `indicator` | Значок статуса | пара к `status` |
| `additional_indicator` | Значок доп. статуса | пара к `additional_status` |

Колонка `execution_deadline` в БД **не участвует**. Срок исполнения для правил — только `actual_completion_date`.

Календарный день — **Europe/Moscow** (UTC+3). Сравнение дат без времени: `YYYY-MM-DD`.

## Пары значков

Статусный значок (левый) и колокольчик (правый):

| Правило | `status` | `indicator` | Вид | `additional_status` | `additional_indicator` | Вид |
|---------|----------|-------------|-----|---------------------|------------------------|-----|
| Открыта, срок контроля в будущем | `on_control` | на контроле | серые песочные часы | `on_control` | на контроле | серый колокольчик |
| Открыта, срок контроля сегодня или раньше | `in_progress` | в процессе | жёлтые часы | `in_progress` | в процессе | жёлтый колокольчик |
| Исполнено не позже срока контроля | `completed` | исполнено | зелёная галочка | `on_time` | в срок | зелёный колокольчик |
| Исполнено позже срока контроля | `completed` | исполнено | зелёная галочка | `deadline_violated` | срок нарушен | красный колокольчик |
| Снято с контроля | `unresolved` | не решено | красный треугольник | `deadline_violated` | срок нарушен | красный колокольчик |
| В АЗ «исполнено в ходе аудита» | `completed` | исполнено в ходе аудита | синяя звезда | `on_time` | в срок | зелёный колокольчик |

## Приоритет правил

Считается **первое совпавшее**. Порядок фиксирован в `choose_status_pair` / `computeRecommendationAutoStatus`.

```text
1. Заполнено «снять с контроля»
      → красный треугольник + красный колокольчик
      (даже если есть срок исполнения или звезда из АЗ)

2. Индикатор / флаг «исполнено в ходе аудита»
      → синяя звезда + зелёный колокольчик

3. Есть и срок исполнения, и срок контроля
      execution > control  → зелёная галочка + красный колокольчик
      execution ≤ control  → зелёная галочка + зелёный колокольчик

4. Иначе, если есть срок контроля
      today < control  → серые песочные часы + серый колокольчик
      today ≥ control  → жёлтые часы + жёлтый колокольчик

5. Нет срока контроля и не сработали шаги 1–3
      → автоматика ничего не пишет
```

«Сегодня» — календарный день Москвы. `today == control` относится к шагу 4 как «срок наступил» (жёлтая пара), не к просрочке исполнения.

## Перенос срока

Это не отдельная пара значков, а **подмена срока контроля** до шагов 3–4.

1. Берётся **самая поздняя** дата среди всех строк `deadline_extensions` и legacy `extension_1_date` / `extension_2_reason`. Порядок строк и то, какой перенос добавлен последним, не важны: при нескольких переносах в «Срок контроля» всегда попадает максимальная дата.
2. Если дата есть, она записывается в `deadline` карточки (и в payload при save).
3. Дальше правила идут уже с этим новым сроком контроля.

Пустые строки переноса (ни даты, ни комментария) игнорируются. Комментарий без даты срок контроля не двигает.

На карточке это делает `applyRecommendationFormAutoStatus`: поле «Срок контроля» сразу показывает дату переноса. На save то же делает `overlay_computed_status_fields`. Ночной прогон — `apply_computed_status_to_recommendation`.

## Снять с контроля

Считается заполненным, если у любой строки `control_removals` есть дата **или** непустой комментарий (то же для legacy `remove_from_control_date` / `remove_from_control_comment`). Пустая заготовка строки в форме не считается.

Шаг 1 сильнее срока исполнения: зелёная галочка сменится на красный треугольник.

## Импорт из АЗ

`POST /tools/parse-recommendations` отдаёт черновики. Превью (`buildParsedPreviewItem`) вызывает те же правила:

- в сроке фраза «исполнено в ходе аудита» → шаг 2, `deadline` очищается;
- дата в будущем → серая пара;
- дата сегодня/в прошлом → жёлтая пара.

Срока исполнения в АЗ нет, переноса и снятия тоже нет. После `batch` backend ещё раз прогоняет overlay.

## Когда пересчитывается

| Событие | Где |
|---------|-----|
| Смена срока контроля на форме | `setField('deadline')` → `applyRecommendationFormAutoStatus` |
| Смена контрольной зоны (исполнение, перенос, снятие) | `setClosure` → тот же helper |
| Create / PATCH рекомендации | `overlay_computed_status_fields` в `recommendations_service` |
| Импорт превью / правка срока в превью | `checkRecommendationsPreview.ts` |
| Каждый день 00:05 Europe/Moscow | `refresh_recommendation_statuses` по всем строкам |

Выключить ночной цикл: `SOKOL_STATUS_SCHEDULER=0`. В pytest цикл выключен всегда.

Любой PATCH (даже только `name`) снова прогоняет overlay: открытые серые сами станут жёлтыми, когда срок контроля наступит, без участия пользователя.

Текущие `status` / `additional_status` **не защищают** от пересчёта. Исключение по смыслу — шаг 2 (звезда), пока индикатор остаётся «исполнено в ходе аудита» и нет снятия с контроля.

## Реализация

### Backend

`collect_auto_status_facts` собирает из payload+existing или из ORM:

- исходный `deadline`, `actual_completion_date`;
- `latest_extension`;
- `removed_from_control`;
- текущий `indicator` (для звезды).

`effective_deadline = latest_extension or deadline`.

`choose_status_pair` возвращает замороженный `StatusPair` (четыре поля). Overlay пишет `deadline`, если был перенос, затем копирует пару в payload. Apply на ORM делает то же и возвращает `True`, если строка изменилась.

### Frontend

`computeRecommendationAutoStatus` — те же четыре шага и те же константы пар. Карточка не собирает факты в хуке: `useRecommendationForm` вызывает только `applyRecommendationFormAutoStatus`.

Иконки — отдельный слой отрисовки: `indicator` / `additional_indicator` → Lucide в `indicatorIcons.ts`. Цвета не считаются в правилах, только подписи.

### Согласованность

Меняя правило, поправить **оба** compute-модуля, тесты с обеих сторон и эту страницу. Расхождение Python/TS сразу видно в таблице рекомендаций: превью/форма покажут одно, после save или ночи — другое.

## Типовые сценарии

1. АЗ, срок 15.10.2026, сегодня 28.09.2026 → серые. 16.10 ночной прогон → жёлтые.
2. Аудитор ставит срок исполнения 10.10 при контроле 15.10 → зелёная галочка + зелёный колокольчик.
3. Срок исполнения 20.10 при контроле 15.10 → зелёная галочка + красный колокольчик.
4. Перенос на 01.12 при жёлтой открытой → `deadline=01.12`, снова серые, пока 01.12 не наступит. Два переноса 01.10 и 01.12 (в любом порядке) → `deadline=01.12`.
5. «Снять с контроля» после исполнения → красный треугольник + красный колокольчик.
6. В АЗ вместо даты «исполнено в ходе аудита» → звезда + зелёный колокольчик; снятие с контроля всё равно перебивает на красную пару.
